## 2. Security

Deployment lens: a loopback-bound service on a single-operator lab workstation,
authenticating with `windows-local`. Findings are ranked for what they would
mean on a shared or production host. §5 lists what is deliberately relaxed in
the lab.

**What holds (verified):** the service binds loopback only, and a connection
from the LAN is refused; session tokens (256-bit, SHA-256 at rest) and API keys
(PBKDF2) are stored hashed; the session cookie is `HttpOnly`, `SameSite=Lax`,
with a 12-hour sliding lifetime; request logs mask query values (#157); HTML
output is escaped throughout (a scan found no raw concatenation, and one
`|safe`, on a constant); SQL is parameterised; subprocesses take argument
lists; identifiers are validated before they reach a path, including
`git_repo.device_path`; an unknown risk word fails closed (#397); device- and
demo-supplied text in the chat context sits inside unforgeable untrusted-data
fences (#167, #191).

### S-1 ☐ [High] Sensitive device operations are classed `normal` and run with no approval — [#526](https://github.com/dnobj/admz/issues/526)

The gate resolves a confirmation level from the operation's catalog
`risk_level` alone ([operations.py](../../admz/operations.py),
`resolve_confirmation`), and `normal` resolves to `none`
([confirm_policy.py](../../admz/confirm_policy.py)). The pinned catalog
(`635c395`) classes 101 VAPIX operations `normal`. Most are harmless. Among
them: `network-settings:setIPv4` and `setDNS`, the resolver, hostname and proxy
setters, `ntp.cgi:setNTPClientConfiguration`, `firewall:deactivate`,
`cert:installCertificate`, the SNMP and remote-syslog setters,
`io-portmanagement.cgi:setPorts` (a door relay), `siren_and_light.cgi:start`,
the MQTT client setters, `action-service:AddActionConfiguration` (which also
walks around ADMZ's own gated rule tools), the privacy-mask setters,
`firmwaremanagement.cgi:commit`, and `param.cgi:update`, which is one id for
every parameter on the device.

Any admitted caller can run these inline, and so can the chat model. Since
device-supplied text reaches the model, this list is the blast radius of a
successful prompt injection. #165 and #365 are the same class, found one
operation at a time.

**Direction:** reclassify in the catalog; add a raise-only, parameter-aware
floor in the gate for `param.cgi:update` (the risk is in the parameter name);
pin the set of ids allowed at `normal` with a guard test.

### S-2 ☐ [High] An API key carries its creator's approve and reveal authority — [#527](https://github.com/dnobj/admz/issues/527)

A key inherits its creator's groups
([api_keys.py](../../admz/api/routes/api_keys.py)). `principal_can_approve`
and `principal_can_reveal` ([authz.py](../../admz/authz.py)) check groups and
never ask how the principal authenticated. So an administrator's key approves
`url_only` gates and reads plaintext credentials with no person present.
`scopes` is stored and never read. Keys do not expire by default. Any
authenticated principal, a key included, can mint and revoke keys. Keys have
no page, so nobody sees a list.

The lab had the live instance: a development key in the approver group, valid
for five months with no expiry and its plaintext in a file. It was revoked on
2026-11-11 (§8). #409 already asks what should separate a development install
from a production one here.

**Direction:** approving and revealing require an interactive principal;
enforced scopes; a default expiry; key management needs an admin scope and a
session; a Settings page.

### S-3 ☐ [High] Credentials go to an address, not to a device — [#528](https://github.com/dnobj/admz/issues/528)

TLS to devices is unverified by default
([ssl_config.py](../../admz/ssl_config.py)) and nothing records which
certificate a device presented. The executor relearns the auth scheme from the
peer's own challenge and will switch to Basic over HTTPS
([vapix.py](../../admz/executor/vapix.py), `_send_self_healing`; #171 refuses
this only over plaintext HTTP). A host that answers at a registered device's
address can therefore choose the challenge and be sent that device's stored
`admz` password in a readable form. Onboarding tries entry credentials, the
fleet root password among them, against an address before anything has
established what the peer is. #326 is this gap on the reprovision path.

**Direction:** an ADR. Measure what devices present on `:443`, then pin the
certificate on first use, or verify the manufacturer's device-identity
certificate where there is one. A mismatch stops credentialed requests, raises
a notice and offers one gated "accept" action.

### S-4 ☐ [Medium] An unrecognised `ADMZ_AUTH_BACKEND` turns authentication off — [#529](https://github.com/dnobj/admz/issues/529)

`_resolve_backend_name` ([auth.py](../../admz/auth.py)) logs a warning and
returns `none` for a value it does not know, so a typo in the service
definition starts ADMZ anonymous. **Direction:** a startup error; `none` stays
available by name or by default.

### S-5 ☐ [Medium] Any Windows account on the host gets a session — [#530](https://github.com/dnobj/admz/issues/530)

Authorization has two group gates, reveal and approve. Everything else is open
to every account that can sign in, which on a workstation includes
unprivileged sandbox accounts. With S-1, such an account can change device
settings. **Direction:** an optional sign-in allow-list; unset keeps today's
behaviour.

### S-6 ☐ [Medium] 6 of 104 state-changing routes check the request's origin — [#531](https://github.com/dnobj/admz/issues/531)

`check_same_origin` ([csrf.py](../../admz/csrf.py)) is called from six
handlers and no middleware. The rest rely on `SameSite=Lax`, which does not
separate one localhost port from another. The voice WebSocket does not check
`Origin` at all. **Direction:** one middleware, the same check at WebSocket
accept, and a guard test over the route table.

### S-7 ☐ [Low] `/api/docs` and `/api/redoc` render blank — [#532](https://github.com/dnobj/admz/issues/532)

Found on 2026-11-10. Both pages load their assets from a CDN, and the CSP from
#200 blocks them. The auth exemption for `/api/openapi.json` names a path that
does not exist; the schema is at `/openapi.json` and does require sign-in. So
nothing is exposed, and nothing works. **Direction:** vendor Swagger UI, or
turn the pages off.

### S-8 ☐ [Low] CLI key management loses a plaintext and writes no audit row — [#533](https://github.com/dnobj/admz/issues/533)

Found on 2026-11-10. `python -m admz api-key create` raises
`UnicodeEncodeError` on a cp1252 stdout after the key row is committed and
before the plaintext is shown. CLI create and revoke record no audit event;
the REST routes do.

### S-9 ☐ [Low] The CSP keeps `'unsafe-inline'` — #277 (already tracked)

Unchanged, and correctly described in
[security_headers.py](../../admz/security_headers.py).

### S-10 ✅ [High] The production tree was writable by every local account — #442

Open at the time of the review. Fixed by the owner on 2026-11-10 (§8).

## 3. Operations

### O-1 ☐ [High] There are no backups — [#534](https://github.com/dnobj/admz/issues/534)

The deployment guide says the database and its key must be backed up
together. Nothing does it. On the reference install the newest copy of the
database was five months old, and the config history (close to two thousand
commits) has no remote. Since ADR-0068 the per-device `admz` password exists
only in that database. **Direction:** `admz backup` and a checked restore, run
as a scheduled task that raises a notice when it goes stale.

### O-2 ☐ [High] Production runs dependency versions CI never tested — #426, #233

| Package | Production venv | Dev venv | `requirements.txt` |
|---|---|---|---|
| fastapi | 0.141.1 | 0.129.0 | `>=0.104.0,<1` |
| starlette | 1.3.1 | 0.52.1 | `>=0.52,<0.53` |
| pydantic | 2.13.4 | 2.12.5 | unbounded |
| python-multipart | 0.0.32 | 0.0.22 | `>=0.0.6,<0.1` |
| anyio | 4.14.2 | 4.12.1 | unbounded |

CI installs from `requirements.txt`, so it tests the declared range.
Production's venv is outside that range for starlette, a package ADMZ imports
directly, and `pip check` does not notice because it compares installed
packages with each other and not with the file. #426 already records the
divergence; the measurement is repeated here because it had not moved in three
months. There is no lockfile and no vulnerability scan.

**Direction:** align forward to what production runs, lock it, build
production's venv from the lock, and have `tools/environments.py` compare an
environment's venv with the declared bounds.

### O-3 ☐ [Medium] Deploying is a procedure held in session notes — #426, #377

The September deploys followed a careful sequence (pre-flight diff of
dependencies and catalog pin, an import walk on production's interpreter in a
throwaway worktree, restart, a health wait that checks the build marker,
automatic rollback, a post-deploy log scan and a function check on a throwaway
data folder). None of it is in the repo. It is now written into #426.

### O-4 ☐ [Medium] Twelve days of logs — [#535](https://github.com/dnobj/admz/issues/535)

Five 10 MB files, each filled in about two days, mostly by `httpx`
per-request lines. **Direction:** `httpx` at WARNING, or request lines in
their own file.

### O-5 ☐ [Low] The environments checker reports a healthy production as "not listening" — [#536](https://github.com/dnobj/admz/issues/536)

Found on 2026-11-11. From the non-elevated shells agent sessions get,
`netstat` lists no system-owned listener, so the checker exits 1 while
`/api/health` answers. Not established: whether an ordinary terminal sees the
same.

### O-6 ⏭ Staging has not run since August — #238

Unchanged. Still a decision: rebuild it, or retire it and verify on dev
instances.

**Observed once, no finding:** a single `sqlite3.OperationalError: disk I/O
error` in the scheduler's reconcile loop on 2026-10-30. It did not recur. It
is recorded in #538 as one more reason to have a single place that sets
SQLite timeouts.

## 4. Architecture

### A-1 ☐ Tool bodies never left `ADMZMCPServer` — [#537](https://github.com/dnobj/admz/issues/537)

ADR-0039 made dispatch table-driven and planned to relocate each handler into
its module. That last phase was not done:
[dispatch.py](../../admz/mcp/dispatch.py) holds 83 shims that delegate to
methods on one class in a 6,094-line file. ACS Pro's module shows the intended
shape. A third module will follow ACS Pro's shape, so the gap widens.

### A-2 ☐ Stores cannot make a write conditional on what they read — [#538](https://github.com/dnobj/admz/issues/538)

Carries forward D-4. Twenty store classes, 63 `sqlite3.connect` call sites, no
shared base, and no compare-and-set or claim primitive. This is why two
schedulers double-fire (ADR-0073 removed the second scheduler instead), why
#523 had to be designed around a lost update, and why #6 is still open.

### A-3 ☐ Rollback is collected and cannot be run — [#539](https://github.com/dnobj/admz/issues/539)

Carries forward B-2. Plan results report `rollback_available`; nothing
executes one. Build it together with #445's read-back, or stop collecting.

### A-4 ☐ Device identity is not a concept ADMZ has

The same finding as S-3, seen from the design side: a device is a registry row
with an address, and "is this still that device" has no answer anywhere in the
model. #528.

**Unchanged and still fine as they are:** the Vault backend stays stubbed
(H-4, deferred until Vault is adopted); the import-time singletons have a plan
(`plans/lazy-store-singletons.md`).

## 5. Lab conveniences that stay

The owner's decision on 2026-11-10: the reference install is a development
lab, some of its settings exist to make development easier, none of them would
be active in a production deployment, and they stay. This table is the
review's reading of what that covers. None of these is filed as a defect.
[#540](https://github.com/dnobj/admz/issues/540) (deferred) is the list a
production install would be checked against.

| Setting on the reference install | Why it is there |
|---|---|
| The service runs as LocalSystem | No service password and no user profile (ADR-0042) |
| The operator's everyday account has full control of the data folder, which holds the database and its key | The operator, and tools running as them, can inspect the database and logs without elevation |
| The operator's everyday account can modify the production code tree | A deploy runs without elevation |
| The encryption key is a file beside the database | Zero-configuration start (ADR-0010) |
| Development and coding-agent sessions run as the operator's account | It is a workstation |
| `dev-only` capabilities exist and can be switched on by environment | Unattended end-to-end tests (ADR-0052). None is on in production |

Not in the table: #442's last open point, that the development tree itself is
writable by every local account. Nothing has established that any tool depends
on it, so it is an open decision for the owner and not a recorded convenience.

One convenience did not stay: the development API key in S-2, revoked at the
owner's request.

## 6. Switches

Asked alongside the review: how to fold the owner's working AXIS T8516 tool
(port map, PoE control) into ADMZ, given that sites will not always use T85
switches and will often have several, in a hierarchy or a chain.

The lab already shows what ADMZ cannot say today. A PoE budget refusal left two
devices dark, and the most ADMZ could say about its own was "unreachable". Four
Axis devices sit on the switch that ADMZ does not manage. The two devices ADMZ
lists as unreachable are on none of the switch's ports.

The proposal is ADR-0074, proposed in
[#542](https://github.com/dnobj/admz/pull/542) and not yet accepted: a third
module with a driver contract, a vendor-neutral topology ADMZ derives from MAC
tables and LLDP, and PoE control behind the gate with the blast radius named on
the approval card. #15 tracks it.
