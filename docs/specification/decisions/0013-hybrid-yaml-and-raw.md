# ADR-0013: Hybrid YAML + raw-response artifact format

**Status:** Accepted, in production.
**Date:** Original design 2026-04 (`EXPERIENCE_CENTER_CONFIG_MANAGEMENT.md`).

## Context

A snapshot of a device produces an artifact stored in git. Two tensions
shape the artifact format:

1. **Humans review configs in git** — they want clean diffs,
   alphabetically-sorted keys, consistent formatting. Raw `param.cgi?action=list`
   output is a flat key-value text dump with thousands of lines, no
   ordering guarantees, and is unreadable in a PR.
2. **Restore must be faithful** — if we normalize the response into
   a clean structure for diffing, we may lose fields the firmware
   added that we don't know about, or shape the data in a way that
   isn't bidirectional (writes look different from the reads).

Either choice alone fails one constraint.

## Decision

Snapshot writes **both forms** to git for every facet:

```
fleet/<device>/
  config/
    image.yaml          # normalized — clean, sorted, diff-friendly
    network.yaml
    stream-profiles.yaml
    users.yaml          # usernames + roles, NO passwords
    ...
  raw/
    image.yaml          # raw API response, preserved as-is
    network.yaml
    stream-profiles.yaml
    ...
  device.yaml           # model, firmware, location, tags
```

The **normalized** YAML is what humans review. It's generated by each
facet's `serialize()` method from the raw API response. Reviewers read
PRs against this; diffs are clean.

The **raw** YAML is the unmodified API response (text dump for
`param.cgi`, parsed JSON/XML for richer formats). This is the
authoritative source. If a snapshot taken from the same unchanged
device produces a different normalized output than expected (because
the facet adapter has a bug, or a firmware change introduced new
fields), the raw is what restore replays.

When raw and normalized disagree at restore time, **raw wins**.

## Consequences

**Positive:**
- Clean diffs for humans: PR reviews see `image.yaml` change from
  resolution `1920x1080` to `3840x2160`, not a 4,000-line raw dump.
- Faithful restore: replaying the raw response handles edge cases
  (encoding quirks, parameters the normalizer doesn't know about,
  firmware-specific extensions) that normalization might drop.
- Forward-compatible: a new AXIS OS major release adds parameters
  we haven't yet built normalizers for — they appear in raw, restore
  works correctly, and we add the normalizer to the facet adapter
  on our schedule.
- Stable serialization rules (keys alphabetized, no timestamps, no
  volatile fields) make snapshots reproducible — taking a snapshot
  twice from the same unchanged device produces byte-identical
  commits, which is what makes diff-detection useful.

**Negative:**
- Storage cost roughly doubles per facet. Acceptable — text data, gits
  delta-compress well, even years of snapshots stay small relative
  to disk.
- The raw form is ugly to review. Reviewers learn to look at the
  normalized side and trust that raw stays consistent.
- Two formats means a facet adapter has to implement both directions:
  serialize (raw → normalized) and deserialize (normalized → write
  params). The framework provides `SimpleParamFacet` to amortize the
  common case (param-prefix-based facets get both directions for
  free).
