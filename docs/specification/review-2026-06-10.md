## 1. Top findings (verified, ordered by severity)

### C-1 ✅ [Critical] Gated plans created in chat cannot be executed by web approval
`PlanEngine._plans` is an in-memory, per-process dict
([engine.py:42](../../admz/plans/engine.py)), but confirm sessions are shared
SQLite. `execute_gated_plan` stores only `plan_id` + summary in the session
([operations.py:509-510](../../admz/operations.py)); on approval,
`execute_approved_session` calls `plan_engine.run_plan(session.plan_id)`
(operations.py:389) **in the uvicorn process**, whose engine never saw a plan
created inside a pooled MCP chat subprocess → `ValueError: Plan not found`
(engine.py:170) rendered as the approval outcome. The single-op path works only
because full op params live in the session row.
**Fix direction:** persist plans (SQLite store like `ConfirmStore`) or
serialize full plan steps into the confirm session and rebuild on approval.
**Test gap:** no cross-process plan-approval test exists (all tests share one
engine instance).
**Fixed (2026-06-10):** took the serialize-into-session route — new
`plan_steps_json` column on `confirm_sessions`; `execute_gated_plan` stores
`PlanStep.to_dict()` for every step; `execute_approved_session` reconstructs
the plan via `PlanEngine.register_plan()` when the in-memory lookup misses.
Cross-process approval test added (`test_operations_core.py`).
**Residual (minor):** plan *status* is still per-process — after web approval
runs the plan in uvicorn, the creating subprocess's copy stays
`pending_approval`, so a later `get_plan_status` from the same chat reports
stale state. Cosmetic (the plan has executed; the approval page showed the
results); a shared plan store (v2 of this fix) would close it.

### H-1 ✅ [High] Every pooled MCP chat subprocess runs its own SnapshotScheduler
`ADMZMCPServer.run()` starts the scheduler
([server.py:3757](../../admz/mcp/server.py)); the chat pool spawns
`python -m admz mcp` per principal and keeps it alive
([mcp_bridge.py:81](../../admz/chatbot/mcp_bridge.py)). uvicorn + N chat
principals = N+1 schedulers firing every enabled schedule: duplicate
snapshot/drift/survey jobs, concurrent git commits (index.lock contention), and
`schedules.json` clobbered by non-atomic `_save()`
([scheduler.py:443-449](../../admz/snapshot/scheduler.py)). This re-creates
cross-process the duplication that tracker item 3.1 fixed in-process.
**Fix direction:** don't start the scheduler when spawned by the pool
(`ADMZ_PRINCIPAL_*` env present), or single-writer election via the DB.

### H-2 ☐ [High] `admz/api/__init__.py` builds the whole FastAPI app on import
`from admz.api.main import app` at package import (verified) means importing
the "leaf" `admz.operations` (which imports `admz.api.confirm_store`)
constructs the FastAPI app, parses CORS env, and registers all routers — in
every MCP subprocess. The operations→api→routes cycle is avoided only by
function-level imports in routes.
**Fix direction:** empty the package `__init__` (lazy `__getattr__`), or move
`confirm_store`/`capture` out of `admz/api/` into a leaf package.

### H-3 ✅ [High] Executor `file_path` = arbitrary server-file exfiltration to a device
`_build_multipart` takes the upload path straight from caller params
([vapix.py:557](../../admz/executor/vapix.py)) and `execute()` opens it
(vapix.py:105-114). Any multipart op via `execute_operation` can read an
arbitrary host file (e.g. `~/.admz/admz.key`, the SQLite DB) and upload it to a
device the caller controls. Reachable by a prompt-injected chatbot; the
firmware-upload op is gated, but the *file read* happens regardless of which
file is named.
**Fix direction:** allow-list `file_path` to the firmware cache root
(`~/.admz/firmware`).
**Fixed (2026-06-10):** `_upload_path_allowed()` in vapix.py resolves the
path (symlinks + `..`) and refuses anything outside `~/.admz/firmware` at the
`execute()` open site, returning a failed StepResult with staging guidance
(`download_firmware`/`import_firmware`). 5 tests added (`test_firmware.py`).

### H-4 ☐ [High] Vault backend cannot update devices
`VaultDeviceRegistry` implements neither `update_device` nor
`update_device_info` (verified: only sqlite_backend defines them; ABC raises
`NotImplementedError`). Callers that break on Vault: MCP `update_device`, REST
`PUT /devices/{id}`, `provision_device` (creates the device admin user on the
camera, **then** crashes storing auth info — half-completed provisioning), and
credential-probe store. Recent parity items (created_at, MAC guard, nickname)
*are* implemented in Vault.
**Fix direction:** implement read-merge-write for both methods.

### H-5 ✅ [High] The riskiest executions (url_* web/chat approvals) write no audit rows
`admz/api/routes/confirm.py` contains zero `record_event` calls (verified;
`catalog.py` has 8). The web form and chat-widget approval paths — the ones
that execute dangerous/service-affecting ops — leave no audit trail, while MCP
audits every call and REST audits `catalog.confirm`.
**Fix direction:** extract the duplicated approve-session pipeline (see D-6)
into one helper and add `record_event` there.
**Fixed (2026-06-10):** did exactly that — shared `_approve_session()` helper
runs the whole gate (rate limit → session → lockout → password → complete →
execute) for both the HTML form and the JSON chat twin (closing D-6's confirm
twin item too), and writes `confirm.approve` (with confirmed_by/risk/level/
is_plan) and `confirm.password_failed` (with locked_out flag) audit rows.
Passwords never reach the log. 4 tests added (`test_chat_confirm_json.py`).

## 2. Architecture (remaining findings)

- **M ☐** Pool reaper can evict an MCP subprocess mid-tool-call: `_evict_idle`
  ignores `entry.lock`; `last_used` refreshes only at acquire/exit
  (mcp_pool.py:359-380, 249-254). A >300s tool phase looks idle.
- **M ☐** Sync SQLite/Fernet/git-subprocess I/O inside async handlers
  fleet-wide (e.g. devices.py:46-59; git `subprocess.run` in snapshot routes;
  sync audit write per MCP call). One slow git/AV stall freezes the event loop
  incl. chat SSE. Direction: `asyncio.to_thread` at registry/git boundaries.
- **M ☐** Eight import-time SQLite-store singletons freeze `ADMZ_DB_PATH` at
  import and have inconsistent test seams (capture.py:369, confirm_store.py:409,
  fleet_settings.py:204, audit.py:206, usage.py:234, sessions.py:217,
  drift_alerts.py:398, fleet/health.py:287). Direction: uniform lazy accessors.
- **M ☐** MCP tools split is schema-only: `MIGRATED_TOOLS` declares schemas but
  handlers + ~45-branch elif stay in server.py. Mitigant: dispatch is unified,
  so audit/validation wrap migrated and inline tools identically. Missing: a
  list_tools↔dispatch parity test (a drift today yields generic InternalError).
- **L ☐** `server.py:2575` imports private `_parse_since` from a REST route
  module (MCP→routes dependency). Move to a leaf.
- **L ☐** Password-attempt lockout and rate limiter are per-process dicts while
  confirm sessions are cross-process SQLite (confirm.py:34-57) — second
  instance on 4243 resets counters. Acceptable single-process; flag for IWA era.
- **L ☐** Unobserved fire-and-forget: `asyncio.create_task(stack.aclose())`
  unreferenced (mcp_pool.py:304); `SnapshotScheduler.stop()` cancels without
  awaiting (scheduler.py:285-289).
- **L ☐** 47 distinct `ADMZ_*` env vars parsed ad-hoc per module; requirements
  are all `>=` floors with no lockfile (google-genai/mcp major bumps break).
- **L ☐** Audit policy asymmetry by drift: MCP audits reads, REST doesn't.
  Document the intended policy.

**Verified healthy:** gate parity is real (MCP/REST/web all delegate to
operations.py, `enforce_url_flow_block` on both passwordless surfaces);
Components/AppContext is one builder, not two sources of truth; no api↔mcp
import cycle besides H-2; recovery.py is a genuine leaf; CR-4/CR-5 audit +

## 3. Security (remaining findings)

Deployment lens: localhost lab tool today (`ADMZ_AUTH_BACKEND` unset →
anonymous), IWA-fronted later.

- **M ☐** Unlimited Gemini spend by default: budget `0 = unlimited`
  (chat.py:806-814) and under NoAuth all callers share the `anonymous` bucket
  (auth.py:167-174). Any local process can burn API spend via `/api/chat`.
  Ship a non-zero default daily budget.
- **M ☐** SSRF-by-design: `test_device_credentials` / discovery accept
  arbitrary hosts/subnets and try built-in default creds
  (credential_probe.py:33, routes/discovery.py:38-67) — fine for a LAN tool,
  but gate behind a real principal + optional CIDR allow-list once IWA lands.
- **L ☐** Fernet key on Windows: `os.chmod 0o600` is a no-op
  (sqlite_backend.py:60-64, `except OSError: pass`); the key also encrypts the
  survey GitHub PAT. Set an explicit owner-only ACL (icacls) at creation;
  document rotation.
- **L ☐** LDAP filter injection: `sAMAccountName={name}` unescaped
  (ldap_groups.py:199-201); input is proxy-trusted REMOTE_USER, so low — use
  `escape_filter_chars`.
- **L ☐** Capture `complete_session` is get-then-update (TOCTOU window;
  capture.py:236-252) unlike confirm_store's atomic conditional UPDATE
  (confirm_store.py:293-300). Mirror it.

**Tracker corrections (Phase 4):** 4.6 (rate limiting) and 4.7 (password
lockout) are marked 📝 deferred but are **implemented**
(rate_limit.py wired at capture.py:165 + confirm.py:154,329; lockout
confirm.py:40-59). 4.1's ✅ should read "implemented, **opt-in**" — default
posture is anonymous with full read + low-risk write; only 5 destructive
endpoints refuse anonymous. 4.5 (0o700 ~/.admz) is POSIX-only in effect.

**Verified holding:** single-source confirm gate with atomic single-use
256-bit tokens; the credential boundary (no `get_credentials` tool; chat
redaction; survey allow-list redaction; audit arg sanitization; probe
`to_dict` omits creds); no XSS (autoescape on, zero `|safe`, chat.js uses
textContent/escapeHtml); SQL fully parameterized; YAML `safe_load` everywhere;
no `shell=True`; path traversal blocked at three layers
(pydantic/MCP-validation/git_repo identifier checks); API keys
PBKDF2-600k + `compare_digest`; survey GitHub flow is fork-and-PR with
Fernet-encrypted PAT; firmware downloader refuses redirect-to-login;
bind-safety check refuses non-localhost bind under header-trusting auth;
no live secrets in repo/logs/docs.
