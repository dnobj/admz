# THE BOUND RULE (issue #227). Every requirement is `>=F,<C`, where C is the
# next boundary above the version PRODUCTION CURRENTLY RUNS, on that package's
# own breaking axis:
#
#   version >= 1.0   ->  <major+1
#   version 0.y.z    ->  <0.(minor+1)     (under 0.x, the minor IS the major)
#
# Above INSTALLED, not above LATEST. The purpose of the ceiling is that a clean
# `pip install -r requirements.txt` in CI resolves the set production actually
# runs. A ceiling above latest leaves CI green on a set production has never
# executed — which is exactly what #222 caught, when a clean install resolved
# majors ahead of dev and prod and failed 182 tests on both Linux and Windows.
#
# Floors are raised to the installed major (0.x: installed minor) only where
# they sat BELOW it. A floor under the installed major lets a resolver backtrack
# legally install a version this code cannot run.
#
# Four packages deviate from the rule; each says why on its own line:
#   fastapi, mcp (bounds shipped in #223 — unchanged here)
#   python-multipart (0.0.z scheme), google-genai (private API — minor cap)
#
# NOTE: setup.py feeds this file into `install_requires`, so these bounds also
# become the installed distribution's Requires-Dist. They are not CI-only.
#
# Bounding these direct requirements does NOT bound transitives — pydantic,
# starlette, anyio, cffi, h11 and watchfiles remain unbounded except where an
# upstream happens to cap them. This shrinks the rolling surface; it does not
# close it. A constraints file is the proportionate follow-up.

# fastapi and mcp: bounds shipped in #222 and resolved in #223. UNCHANGED by
# #227 — the reasoning below is merged and still current.
#
# fastapi: RESOLVED (#223, Starlette half). ADMZ's 70 `TemplateResponse(name,
#   context)` call sites were migrated to the Starlette 1.x
#   `TemplateResponse(request, name, context)` signature, and the
#   route-inventory tests were ported off the flat-`app.routes` assumption that
#   FastAPI >= 0.130 broke (see tests/route_inventory.py).
#
#   The floor deliberately stays low: both the migrated call signature and the
#   route-inventory helper work on the old AND new router layouts, so
#   production's existing 0.129 venv stays in spec while a clean install now
#   correctly resolves 0.141+. The `<1` cap is the lesson of #222 kept rather
#   than discarded — bounded at the next major boundary, not unbounded again.
#
#   This is the one package where CI does NOT test what production runs: a
#   clean install resolves 0.141 while production stays on 0.129. That is
#   #223's deliberate choice, not an oversight of the rule above.
#
# mcp: RESOLVED (#223, mcp half). The 1.x low-level decorators
#   `@server.list_tools()` / `@server.call_tool()` are gone; handlers are now
#   registered with `add_request_handler(method, params_type, handler)`, take
#   `(ctx, params)`, and return `ListToolsResult` / `CallToolResult`.
#   `Tool.inputSchema` is now `Tool.input_schema` — camelCase survives only as
#   the pydantic serialization *alias*, so `Tool(inputSchema=...)` still
#   constructs (all 35 inline tool definitions were untouched) but attribute
#   reads had to move.
#
#   The floor is 2.0 rather than something lower: `mcp.types` is a shim over the
#   split-out `mcp-types` package from 2.0 onward, and the handler-registration
#   API this code now calls does not exist in 1.x. Unlike fastapi above, there is
#   no signature that satisfies both majors, so this one really is a floor. The
#   `<3` cap keeps #222's lesson rather than discarding it.
#
#   mcp 2.0.0 pins `mcp-types==2.0.0` exactly, so `<3` transitively bounds that
#   too. `mcp-types` is a NEW package that appears in the venv on upgrade.
#
#   Note for whoever raises this next: 2.0 also dropped the SDK-side
#   `jsonschema.validate(arguments, tool.inputSchema)` that 1.x ran before every
#   tool dispatch. admz/mcp/server.py now performs that check itself — do not
#   delete it assuming the SDK still does it.
